# 性能与残余效果音调查

本轮仅调查，未修改运行代码或安装包。检查当前源码、本地 Sounds-2.2.1+1.20.1+forge.jar 字节码、当前两种随机效果池与 sounds/event.json，并运行集合变化模拟。没有报告者的实际效果增删轨迹，以下明确区分代码事实与现场假设。

## 声音的确定事实

1. Sounds 在 CLIENT_LEVEL_PRE 每游戏刻执行 PotionEventHelper.listenForEffectChanges。通过效果 ID 的集合差求新增/消失，并逐个调用 ConfiguredSound.playSound。本方法没有统一节流或合并同帧多条通知。
2. 它不比较同一 ID 的等级或持续时间，单纯强化、续时不会由这个方法直接产生声音。
3. 当前兼容 Mixin 已在最近一次整合包启动日志确认应用。不能因此保证报告者也使用同一 JAR 或同一配置。
4. 兼容范围：穷遐见证的随机正面池与已经存在的 HARMFUL 的消失；幽谷见证的随机池、迅捷、黑暗、失明。新获得的其他负面效果保留提示。穷遐恶意的清除增益不在相应见证屏蔽逻辑内。
5. 当前两种增益池均只有 5 种：跳跃提升、生命恢复、抗性提升、急迫、力量；幽谷另有迅捷。当前穷遐每 5 秒处理 2 次，自动增益持续 5 秒；幽谷攻击触发冷却 3 秒、随机数量 1。
6. Sounds 配置开启正负效果的新增/消失提示。增益获得为 item.trident.thunder，减益获得为 entity.illusioner.mirror_move，正负效果消失均为 item.trident.riptide_1。仅凭“像清 buff 的声音”不能精确判断来源。

## 可以导致反复响声的路径

### A. 持续来源补回减益（全反转且静止时的重点候选）

环境/装备/其他模组持续施加负面效果 → 穷遐自动清除 → 当前兼容消除消失提示 → 原来源重新施加 → 作为新增负面效果播放提示 → 再次清除。

此路径由当前逻辑允许，但没有报告者的效果轨迹，不能断言就是现场原因。需要来源补发在客户端被观察成“消失再新增”；同一次采样之间完成的变化不会触发集合差声音。

### B. 恶意清除与其他装备补发增益（攻击/受击时重点候选）

穷遐尚未反转时，受击可能清除一个或全部增益；其他饰品、光环又重新加回。增益池之外的效果不在当前静音集合中。Sounds 对每个变化分别播放，所以一次 30 个效果消失/补回可以各产生 30 次播放调用。配置音量再小也可能明显叠加。

### C. 不属于苦旅静音集合的效果自行过期或联动变化

现在按效果种类过滤，并非按“真正来源于苦旅”追踪。其他短周期效果，或某效果触发的额外效果，仍可能发声；目前不能归因给苦旅。需要具体 ID 和增删时间才能判断。

大量静态效果本身不会让过滤失效。build/SoundTransitionsTest.java 调用真实 EffectSoundBaseline 并复现 Sounds 的 ID 差分算法，结果：1000 个稳定或仅改变数值的效果产生 0 次通知；静音池效果新增/到期产生 0 次；被清除后重新施加的减益产生 1 次新增通知；30 个非静音增益消失/补回各产生 30 次通知。这是逻辑模拟，不是报告者现场音频复现，也不包含 Sounds 的图标可见性检查。

## 性能热点与建议优先级

### 高关注：效果音兼容的逐刻重复扫描和分配

SoundsPotionCompatMixin.java:53 每刻构建当前效果 Map，遍历旧效果寻找负面项，重新解析静音池，EffectSoundBaseline 再复制旧 Map。随后 Sounds 本身又构建当前 Map 和两个差集 Map。大量效果下重复工作与临时对象明显增加。

建议缓存配置决定的静音 ID 集合；复用 Sounds 已有比较结果，在实际播音处过滤/合并通知，避免另建完整基线。当前为按效果数线性增长，未经 CPU/分配采样不能声称已测得固定帧率损失。

### 高关注：清除失败时尝试次数不受成功次数上限约束

TravailEvents.java:424 的循环以 removed < actions 为条件，而 removed 仅在移除成功时增加。若大量减益被其他模组取消移除，配置只要求处理 2 次也会尝试整个减益列表。随机 ArrayList.remove(index) 还会搬移后续元素，最坏存在平方级搬移成本。

建议随机选择后与末尾交换再移除，消除列表搬移；为尝试次数单独设上限，并在多轮间公平轮换，避免总卡在不可移除的效果上。不要反复尝试同一个效果，也不要强制绕过其他模组的取消事件。

### 高关注：效果变动产生的第三方回调与同步

一次清掉大量效果，会触发多个移除事件、属性更新和网络通知；持续来源下一刻又补回，造成重复处理。苦旅自身集合循环不是全部成本。即使静音，服务器和网络开销仍在。

建议先记录增删频率和取消移除次数。对随机授予中明确不会提升等级或延长时长的操作，考虑跳过，但必须保持原有“每轮处理次数”语义，并评估第三方依赖 Added 事件的兼容性。

### 中关注：结构查询

TravailEvents.java:438 每秒检查所有未完成结构，当前配置每类抽 4 个，六类最多 24 个（还会去重）。查询空间已局部化，但大量玩家静止时仍重复查相同位置。建议缓存维度与方块位置对应的查询结果，移动或结构数据更新后失效；不要只按区块坐标缓存，结构边界可能在区块内部。

### 中关注：随机池缓存命中仍有工作

RuntimePools 每次调用 List.copyOf(source) 并以列表作为 Map 键，需要列表 hash；configuredMaxLevel 每次正面效果添加仍遍历两池。当前每池 5 个，单次成本小，大效果环境若外部每 tick 重加很多效果会放大。

建议按池身份直接保存解析结果，同时预建 effect ID → maxLevel 映射；仍只在配置重载时重建。

### 中关注：物品提示与全局字体钩子

DiaryDialogue 物品提示每次构建仍重新分行测宽，不是上一轮 TravelDiaryScreen 页面缓存的覆盖范围。名称外光晕仍额外提交 16 次文字绘制；Font 钩子对普通文字也会做标记检测并创建小数组。普通未标记文本在首个非空字符退出，不是全量扫描每一行。

建议缓存物品提示正文的静态排版，按窗口宽度、语言、字体资源、玩家名失效；预计算光晕采样偏移，优化普通文字快速路径。保持现有外观，先采样再决定是否减少绘制。

## 后续处理建议

先做受控诊断：短时间聚合记录效果 ID、增加/消失、是否命中静音、实际播音类型；服务端同步记录苦旅清除/给予动作及移除失败数。不要每 tick 打完整效果列表，以免诊断本身制造负载。

确认来源后，对苦旅自动操作精确静音，并对“刚被自动净化、马上又被相同来源补回”的重复提示进行短时合并；保留首次负面效果警告。同帧同类音效只播一次可防叠加，但不应不经用户确认就全局关闭其他效果声音。若采取客户端节流，需明确它处理的是响声，不能解决服务器端的反复补发/移除成本。
