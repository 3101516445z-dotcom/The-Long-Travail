# 无垠之见证栏位刷新问题

检查对象：本地 Curios 5.14.1+1.20.1 JAR 与苦旅代码。

已确认的调用链：

1. 攻击成功可能更新苦旅物品 NBT 中的 `AttackCleanseCooldown` 或 `ValleyWitnessCooldown`。后者在幽谷见证生效且冷却结束时写入；并非每次攻击都必然写入。
2. CuriosEventHandler.tick 比较当前与上次 ItemStack，NBT 变化会走旧物品 `onUnequip`、新物品 `onEquip` 的刷新流程。
3. 原 LongTravailItem.onUnequip 未检查替换物品，直接将无垠新增栏位中的饰品搬入背包，背包满则掉落。即使新旧物品都是同一件仍有无垠见证的苦旅，也会执行。
4. 另有两套栏位来源共用同一 UUID：物品属性回调，以及每秒先删除再添加的服务器逻辑。后者造成无意义的重复刷新，但不能仅凭这一点断言其单独导致脱落；直接清空物品的明确路径是第 3 步。

修复：

- 同种苦旅的数据刷新不再按真正卸下处理，新状态交给 onEquip 对账。
- 移除物品属性形式的栏位加成，只保留一个管理入口。以实际修饰符为准，数值不变则不撤销、不重加。
- 管理器拥有的修饰符持久化，仍在真正卸下、失去见证或减少配置数值时撤销。仅处理苦旅的 UUID，不影响其他模组。
- 登录时对账，旧缓存修饰符就地迁移，避免它在下一次缓存清理时被移除。
- 真正减少容量时先转移受影响饰品，再撤销栏位，保留原背包满时掉落的行为。

验证：生产对账方法以 Curios 接口测试替身执行，覆盖 1000 次相同状态刷新、扩容、减容、实际移除、旧缓存迁移及其他模组修饰符保留。编译通过。此为代码路径分析及回归验证，尚未在完整整合包内进行攻击、重登、死亡复活实测。
