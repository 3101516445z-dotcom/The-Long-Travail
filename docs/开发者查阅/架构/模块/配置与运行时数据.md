# 配置与运行时数据

核对日期：2026-10-24。本章核对 TLT 的配置注册、文件恢复、候选发布和公共配置重载后的运行时刷新入口；没有重新执行配置测试或整合包测试。完整过程见 [配置加载与重载](../链路/配置加载与重载.md)，接口和测试约定见 [公共运行模块](../../runtime-integration.md)。

## 基础能力与协调层

| 职责 | 源码入口 | 边界 |
|---|---|---|
| 注册与装配 | [ConfigFiles](../../../../src/main/java/com/thelongtravail/config/ConfigFiles.java) | 将 TravailConfig.SPECS 注册为 COMMON，将客户端定义注册为 CLIENT；装配默认池补充和监听生命周期 |
| 单文件状态管理 | [ManagedConfig](../../../../src/main/java/com/thelongtravail/config/ManagedConfig.java) | 维护磁盘基线、当前有效配置、是否可写和是否监听；连接 Forge 配置事件 |
| 解析与文件写入 | [ConfigFileIO](../../../../src/main/java/com/thelongtravail/config/ConfigFileIO.java) | UTF-8/TOML 解析、委托排版、临时文件替换；不负责玩法缓存 |
| 定义校验 | [ConfigValidation](../../../../src/main/java/com/thelongtravail/config/ConfigValidation.java) | 按 ForgeConfigSpec 转换、补齐和回退字段；包含动态战利品概率处理 |
| 启动恢复 | [ConfigRecovery](../../../../src/main/java/com/thelongtravail/config/ConfigRecovery.java) | 原始字节备份、默认值恢复、迁移及写前比较 |
| 文件事件 | [ConfigWatcher](../../../../src/main/java/com/thelongtravail/config/ConfigWatcher.java) | 后台监听、事件合并、调用单文件重载；不在此直接刷新游戏世界 |
| 派生数据 | [RuntimePools](../../../../src/main/java/com/thelongtravail/data/RuntimePools.java) | 解析注册表相关池，发布快照并清理探索缓存；同时协调高度惩罚等具体机制 |
| 服务端刷新与展示同步 | [TravailNetwork.onConfigReloading](../../../../src/main/java/com/thelongtravail/network/TravailNetwork.java) | 转入服务端执行队列，刷新机制、菜单及客户端提示快照 |

ConfigFileIO 是文件基础设施；ManagedConfig 是带 Forge 生命周期的管理层；RuntimePools 与 TravailNetwork 已直接依赖具体玩法，属于协调层。新增玩法可以复用前者，但不能把后两者描述为完全独立的通用库。

## 三份状态不能混用

| 状态 | 所有者 | 用途 |
|---|---|---|
| 磁盘原始字节与最近基线 `disk` | 文件系统、ManagedConfig | 检测重复通知和写入期间的外部修改；不是玩家存档 |
| 已发布配置 `active` 与 ForgeConfigSpec | ManagedConfig | 供配置读取；非法字段回退后可以与磁盘内容不同 |
| 运行时快照和缓存 | RuntimePools、各机制、客户端同步层 | 从有效配置和注册表派生；需要刷新、失效或网络同步 |

`RuntimePools.snapshot` 是 volatile 引用，重建完成后一次替换。池条目经过格式及注册表可用性检查；相同目标保留首条，后续重复项记录警告。等级映射和黑名单使用只读副本。这个快照发布不意味着所有配置文件、机制缓存和客户端在同一瞬间完成事务。

## 生命周期与失败边界

- 启动时由 `ConfigRecovery.prepare` 恢复并写入规范化配置；存在问题的原始文件先归档到配置目录的 `invalid` 子目录，并保存说明及核对备份字节。I/O 失败可以阻断加载，不能一概认为总能自动恢复。
- Loading 事件后启动监听；卸载时移除对应文件回调，无剩余文件的目录监听被取消。
- 热重载的字段非法与整份 TOML 无法解析走不同分支，详见链路章。`rejected` 表示禁止本次写回，不表示整份候选不发布。
- `save()` 只在已加载且可写时执行，并比较磁盘基线。`update(edit)` 是内部预设编辑路径：写入后更新配置，但没有显式分发 Reloading 事件，也未复用完整 validate 流程。不能把它当作自动刷新全部运行时机制的通用入口。
- `spec.correct` 可能移除未定义键；排版工具保留未知内容的测试不等于整个加载校验流程保留所有未知配置。

## 新增配置时查什么

先在对应 Spec 定义键、默认值和合法范围，再核对排版与双语说明。随后区分读取方式：直接 `.get()`、预计算池、缓存、客户端提示分别需要对应的更新路径。依赖注册表的值还要检查注册表就绪时机，不能只证明 TOML 可解析。

修改公共配置刷新逻辑时，沿 `TravailNetwork.onConfigReloading` 检查 RuntimePools、GoldenAgeActions、Affection、菜单、RainEvents 和 TooltipConfigPacket；新增缓存必须明确由谁失效。客户端配置不进入这个 COMMON 过滤后的广播流程。

配置规则、预设格式和已有测试入口以 [运行时约定](../../runtime-integration.md) 为准。本轮只检查文档和索引；未宣称 `testConfigLayout`、`testConfigRecovery`、`testConfigDiagnostics` 或真实热重载通过。

## 配置结构更新（第十、十一轮）

ManagedConfig 保留锁、校验、入口差异和异常策略；ConfigFileIO.writeChecked 负责有版本检查的写盘，publish 负责运行时发布。[ConfigDefaultEdits](../../../../src/main/java/com/thelongtravail/config/ConfigDefaultEdits.java) 提供列表默认值编辑能力，applyLive 明确完美流体现有的先改活动配置策略，不能用它替代普通 update 的候选隔离路径。详见 [默认池链路](../链路/默认池初始化与更新链路.md)。
