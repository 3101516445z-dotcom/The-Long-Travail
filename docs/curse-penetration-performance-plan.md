# 受击诅咒、流体穿透与下一轮性能改进

> 历史候选方案：下文保留讨论过程，战斗规则已由后续确认的 [当前实现](combat-rules.md) 替代；性能改进见 [实施记录](performance-improvements.md)。

状态：设计分析，未实施本文的事件、伤害或性能改动。前一轮视觉生命周期与任务池修复保留。

依据：当前源码、当前 Forge 1.20.1-47.4.20 本地源码补丁，以及当前安装的旧梦遗物 1.0.3 字节码。性能部分是静态热点分析，不是实际 CPU/GPU 测量结果。

## 2：明确保留“攻击尝试触发诅咒”

规则：攻击只要进入对应的攻击事件，就应尝试触发诅咒；后续取消伤害、完全减伤或吸收生命不应自动免除诅咒。受害者惩罚与攻击者的“成功造成伤害”奖励可以使用不同阶段。

旧实现把 `processBeingAttacked` 与窒息免疫、禁空攻击取消放在同一个 HIGHEST 监听器中。它先执行诅咒，随后可能取消伤害；这与上述规则一致，不应后移到 LivingDamageEvent。

建议拆成两个职责明确的监听器：

1. 诅咒观察器：`@SubscribeEvent(priority = EventPriority.HIGHEST, receiveCanceled = true)`；仅在服务端检查装备并执行现有诅咒流程，不修改攻击事件的取消标记。
2. 攻击规则处理器：保留现有免疫、禁空等取消逻辑，不再执行受击诅咒，不给普通攻击恢复放行。

`HIGHEST` 控制相对顺序；`receiveCanceled` 控制是否接收已经取消的事件，二者不是替代关系。同优先级的其他处理器可能先取消事件，显式接收可填补当前监听器的这个缺口。拆分之后必须删除旧入口中的诅咒调用，保证每次事件只执行一轮。

不顺便加入冷却、零伤害过滤、对本模组免疫伤害的豁免，也不更改概率或随机调用顺序。这些都是平衡变化。

边界：

- 若某个模组在攻击事件发布之前直接截断 hurt，监听器无事件可接收。
- 接收已取消事件不等于强制成功移除药水效果；当前 EffectChanges.remove 仍遵循效果移除事件的结果。
- 视觉剥夺的独立状态使其不依赖药水应用成功，这与其他诅咒子效果的执行边界不同。

回归矩阵：在观察器前后分别取消攻击、取消前已存在正面效果、本模组窒息免疫、禁空攻击、无装备、客户端、重复注册检测。验证诅咒调用一次、伤害仍取消、没有普通伤害被恢复。不要用依赖概率的测试判断是否执行；固定测试配置或记录调用。

## 4：流体伤害的穿透范围

简化链路（省略分支，不代表所有 hurt 都会到达每一层）：

```text
TrueDamage.hurtFluid -> ServerPlayer/Player.hurt
  -> 更早的服务端保护或第三方注入可能返回
  -> ForgeHooks.onPlayerAttack / LivingAttackEvent
       -> 现有 Mixin 对自身流体伤害恢复该钩子的放行结果
  -> 后续实体无敌、盾牌、受伤冷却等检查
  -> LivingHurtEvent
  -> 护甲、效果、附魔、吸收生命结算
  -> LivingDamageEvent
  -> 扣血；致死时进入图腾/死亡等流程
```

Player 补丁在 hurt 开头发布攻击事件；不能说此时所有实体免疫检查已经完成。当前 FluidErosionUnavoidableMixin 的相关注释需在后续整理时纠正。

| 机制 | 当前处理 | 边界 |
| --- | --- | --- |
| LivingAttackEvent 取消 | 开启 fluidErosionUnavoidable 时，对自身流体伤害恢复钩子返回值 | 不撤销监听器已执行的副作用，也不会重放此前因事件取消而被跳过的监听器 |
| 虚空项链的无来源伤害免疫 | 它在上述事件中检查来源实体为空并取消，当前返回钩子覆盖这个拦截位置 | 依据已检查的 1.0.3 字节码；不是所有未来版本保证 |
| 护甲、抗性、保护附魔、盾牌、通常的受伤冷却 | 对应伤害类型 bypass 标签 | 适用于遵循这些标签的路径，不约束任意第三方代码 |
| 吸收生命 | Player.actuallyHurt 中定点改变计算时读取的吸收量 | 原吸收生命不作为这次伤害的抵扣额度，不以临时清空再恢复的方式修改全局状态 |
| LivingHurtEvent 的取消、归零、减伤 | 不强制恢复 | 仍可能抵消侵蚀 |
| LivingDamageEvent 的取消、归零、减伤 | 不强制恢复 | 仍可能抵消侵蚀 |
| 更早的 hurt 注入、isInvulnerableTo、创造无敌等 | 不提供通用绕过保证 | 本伤害未声明 bypasses_invulnerability；具体第三方路径要检查 |
| 图腾、LivingDeathEvent 取消、死亡保护 | 不强制绕过 | 原有测试确认原版图腾可生效 |
| 自定义生命系统、强制锁血、伤后回填生命 | 不覆盖 | 即使伤害事件放行，也不能保证最终生命下降 |

关闭 fluidErosionUnavoidable 只关闭该攻击事件返回钩子的强制放行，不会同时撤销其他伤害标签和吸收生命绕过。

建议把可选扩展分为三个层次，不混称“绝对真伤”：

- 当前范围：穿透攻击事件取消和常规防御，继续保留后续事件与死亡保护。
- 扩展范围：对自身侵蚀在 Hurt/Damage 两个阶段定义最低伤害结果；这还必须明确保留正向增伤还是固定侵蚀量、如何区分减免与增伤，不应简单覆盖原始数值。它会改变伤害结算规则，并保留监听器副作用问题，需要独立开关与测试。
- 强制生命/强制死亡：属于不同玩法和更强干预，不作为性能优化或修复顺手加入。

按照“对抗整合包中的通用无来源伤害免疫”这一目标，当前通用且限定自身伤害类型的钩子比只针对虚空项链打补丁更贴切。伪造攻击实体会改变归因、PVP 与反击逻辑；直接 setHealth 又绕过正常伤害流程，均不作为默认替代。

## 性能改进：按风险和可验证收益分阶段

### A. 周期任务错峰

当前 isDue 只使用世界时间取模，远方见证和流体伤害在同一 tick 对全部玩家触发。幻翼扫描已经加入 UUID 偏移。

建议对其他周期任务采用稳定的 UUID 与任务类型偏移，周期为 interval 时使用 `floorMod(gameTime + phase, interval) == 0`。每种任务采用不同稳定偏移，避免同一玩家的不同周期任务又总撞在一起。

保留每 interval tick 一次、每轮动作数与随机抽取逻辑。改变的是触发相位，因此首次触发时点会变化，并可能改变与其他事件的相对顺序；不应声称完全零行为差异。interval=1 时无法错峰，也不会降低总工作量。

验证连续多个周期中每人的执行次数不变、间隔不变、负 UUID 哈希不出错、周期为 1、配置重载与重登不产生补发风暴。测每 tick 峰值与 P95/P99 MSPT，不能只看平均值。

### B. 高空减速缓存

AltitudePenalty 当前使用共享的 synchronized IdentityHashMap，达到 64 项就整表清空。超过阈值且访问交错时，可能反复丢失同 tick 缓存；这是失效策略问题，不能仅通过提高容量永久解决。

优先评估把缓存放到每个 Player 实例的 Mixin 字段中，保存 tick、factor 及必要的失效信息。客户端玩家和服务端玩家是不同实例，不需要所有玩家竞争一张共享表；对象销毁时缓存随之销毁。

需要保留显式失效入口，并验证换维度、重生、卸装备、重置日记、配置更新。现有“同 tick 一致、下一 tick 重算”的语义应明确保留；不要借机长期缓存饰品库存或世界状态。

验证 1/64/65/100 玩家交错读取与单人同 tick 多次读取，统计实际 compute 次数。没有实测前不声称会带来明显 TPS 提升。

### C. 名称光晕的 CPU 开销

正常不透明名称有 16 次光晕文字绘制加 1 次主体绘制。17 次 Java 绘制调用不等于 17 个 GPU draw call；共享 render type 可能合批。普通未标记文字的 material 探测会在首个非空白未标记字符处提前退出，也不能说所有界面文字都被完整扫描 17 次。

低风险候选：一次绘制中准备可复用的去标记文本、避免重入时反复做材质识别、名称无需扫描 prose 的 sweepWidth、在确认渲染器同步消费矩阵后复用局部矩阵。当前 unmarked 是惰性包装，仅创建一次 lambda 并不意味着每次渲染都不再逐字转换，真正优化需验证缓存后的格式与字体行为。

保持 16 个光晕采样位置、透明度和颜色不变。不能为了减少 map 分配而全局缓存捕获坐标的 MaterialType，因为 originX、sweepWidth 与延迟提交时的材质状态可能串用。

若实测瓶颈在 GPU 透明叠加，单纯减少 Java 对象不会解决。下一阶段才考虑可选质量档位或单次绘制的光晕着色器。后者需要覆盖字形外边缘、字体图集边界和 Modern UI SDF/描边，不能只改一个 fragment shader 就保证视觉等价。

验证相同分辨率、字体、帧率上限下关闭/开启名称提示，多名称可见、原版字体/字体替换、资源重载；分别测 CPU 分配、帧时间 P95/P99、GPU 时间，并做画面对比。

### D. 极端配置的总工作量

每 tick 64 次效果动作意味着单玩家每秒最多 1280 次添加尝试。4096 件奖励对于最大堆叠数 1 的物品意味着最多 4096 个掉落实体；奖励出现次数还会随击杀数放大。现有数值上限并不是最终工作量上限。

第一步只做一次性配置成本诊断、跳过零动作/空池的无用准备、测量效果尝试数与生成实体数。不合并效果抽取、不减少抽取次数、不更改概率。

对掉落做分批生成只能平滑创建峰值，最终实体仍需要持续 tick，不能宣称解决总实体负载。若引入队列，还要处理全局容量、公平性、区块卸载、玩家离线和服务器停止时未兑现奖励；无限队列只是把问题搬到内存中。

硬上限、丢弃奖励、延后净化或减少诅咒触发都属于规则变化，应与普通性能优化分开讨论。

### E. 高频诊断输出

VisualDeprivation.start 每次成功触发写 INFO。可考虑把逐次日志移到 DEBUG/显式诊断模式，常规运行只保留必要告警。触发、刷新、发包次数保持原样。日志级别变化比降低诅咒判定频率更适合作为第一轮低风险优化。

## 建议落地顺序

1. 受击观察与取消规则拆分，并验证已取消事件也只判定一次。
2. 周期任务错峰、高空缓存失效策略、逐次诊断日志降级。
3. 文字绘制采样，随后做保持画面不变的 CPU 优化。
4. 极端配置的成本诊断；确认确有实际需求后再设计奖励预算或视觉质量档位。

伤害穿透扩展独立于以上性能工作推进，不用更强伤害或更少触发来换取性能。
