# 效果音与高频路径处理设计

状态：研究方案，尚未实现；不修改当前 JAR。依据当前苦旅源码与本地 Sounds 2.2.1 字节码。报告者的现场效果轨迹尚未获得，因此不将某条可能路径认定为唯一根因。

## 一、效果音：实际操作标记、定向过滤、有限合并

### 1. 先建立可关闭的短时诊断

增加默认关闭、自动结束的诊断模式，例如持续 30 秒。服务端按玩家/效果 ID 聚合苦旅增益、净化、恶意清除、移除被取消的计数；客户端聚合新增/消失、静音理由、实际播放类别及效果 ID。每 5 秒汇总一次，不每 tick 输出完整效果列表，不广播其他玩家数据。

该诊断区分：苦旅自发增删；持续来源补回减益；恶意清除后装备补回增益；其他短时效果到期；其他模组独立播放声音。最后一种不是 Sounds 的 PotionEventHelper 过滤能解决的。

### 2. 服务端提供“苦旅实际做了什么”

对苦旅自己的 addEffect/removeEffect 包装操作，记录操作前后的真实效果状态。移除失败不发“已移除”；添加返回 false 或状态未变不产生虚假的新增提示标记。只收集对当前佩戴者的变动，不改全局药水事件。

标记包含效果 ID、变化方向、原因、序号/批次；只同步本人，并与必要的效果状态同步协调。网络协议升为 5，双端一起更新。不每 tick 发送完整效果表，也不向未佩戴者持续发送诊断包。

包顺序是验收重点：不能在原版移除包已经触发声音之后才补发静音标记。实现时需核对原版效果包发送位置，将原因标记与对应效果包有序发送/提交；必要时让兼容层短暂暂存待判定通知（以 tick 为单位、有明确上限），匹配后再决定是否播放。超时无匹配则恢复正常提示，不能长时间静默吞掉未知事件。只依赖连接有序、却不验证原版包和自定义包在主线程的实际顺序是不够的。

同一 tick 发生删除、补回，应按最终客户端可见状态和批次归并；不能简单用一个“最近改动过的 ID 集合”处理多个相反方向的变化。

### 3. 到期及来源冲突

自动赠予效果的自然到期也应静音。服务端维护有限的临时归属记录，关联实际生效的实例/代次、等级、时长；在观察到外部重新添加/覆盖时取消或重算归属。生命周期包括摘下苦旅、死亡、切维度、断线；不把声音归属写入持久 NBT。

原版效果没有通用、永久的“来源标签”。其他模组直接改实例、绕过常规事件时无法保证准确追溯。同 ID 被玩家手动喝药覆盖后，不能继续武断认为全部属于苦旅；无法确认时保留正常声音，并在诊断模式记录归属不明。

### 4. 反复补回的抑制边界

- 苦旅直接产生的自动新增、清除、自然到期：有匹配标记时静音。
- 首次出现的外部负面效果：保留警告。
- 相同负面效果刚被苦旅清除，又在很短时间内补回：首次记录这一循环的提示，随后同 ID 的循环提示限频；建议初始重复提示间隔 10 秒，回填识别窗口 2 秒，作为可调整参数。2 秒窗口可能漏掉较慢补发来源，需据诊断数据调整。
- 不能声称客户端已识别“相同来源”；这里最多确认同 ID、相近时间与苦旅清除动作相关。若玩家离开环境后真正再次受袭，错误静音范围应受短窗口限制。
- 同一苦旅操作批次关联的一批效果提示可合并为一次，避免几十声叠加。不默认对所有其他模组通知全局限频。
- 穷遐恶意清除后装备补发大量增益的声音可类似处理，但不得因此取消恶意本身的清除效果。

### 5. 消除当前兼容的重复全表工作

停止先构建苦旅 current Map、复制 previous Map，再让 Sounds 完整构建一次。优先在 Sounds 得到新增/消失 ID 后、实际播放前过滤通知，保留它自身的状态更新。需要取得当前循环的效果 ID 与方向；若现有字节码不便可靠注入，使用版本限定适配器和目标结构检查，不能仅拦截无参数 playSound 然后猜它对应哪个效果。

静音规则、服务器标记、近期循环记录分别有容量和生命周期限制，过期淘汰；不为每帧位置或每个任意字符串建无限缓存。不同 Sounds 版本不匹配时跳过并警告，避免崩溃。没有 Sounds 时不启用其适配，不改其他音效系统。

## 二、清除失败与大量效果的服务端成本

当前每轮成功次数有限，但失败尝试可遍历所有减益，且随机 ArrayList.remove(index) 搬移数组。

改为：快照后随机索引与末尾交换，再移除末尾；单次处理后的列表操作 O(1)。仍需 O(E) 建立当前候选快照，不能宣传为与效果数量无关。

增加独立尝试预算，建议 max(32, 配置成功次数)，且不超过 64。超过预算的候选进入下一轮公平轮换，不永久拉黑被取消移除的效果。成功次数、尝试次数分开统计，不绕过其他模组的取消事件。

玩法边界：大量被保护效果存在时，原算法可能最终找到可清除项；预算算法可能本轮尚未找到。因此必须定义未用次数是否仍转换为增益（建议沿用当前规则），并在说明中明确这是极端情况下的行为变化。

不建议静默给“受击清除全部增益”增加冷却或数量上限：这会改变恶意强度。先优化自身循环和音效，再根据诊断评估是否需要可配置玩法调整。也不增加效果持续时间来掩盖声音循环。

## 三、随机池查找与效果等级

使用不可变 RuntimePoolSnapshot，固定保存穷遐池、幽谷池、钓鱼实体池、奖励池，按枚举/字段直接访问。构建时预计算：

- effect ID → 两个增益池共同决定的最高等级。
- 每池累计权重与总权重，使用 long；每次按权重随机选择，保持现有概率。

加载/重载时校验并原子替换快照，不在热路径 List.copyOf、计算列表哈希或遍历两池查等级。当前池只有 5 项，此优化主要为大量外部效果反复添加与自定义大池准备，不能夸大为已证实的主要卡顿来源。

“跳过无收益 addEffect”暂不默认实施。原版合并涉及隐藏效果、无限时长、显示标志，穷遐还会先强化传入等级；第三方也可能监听 Added。只有证明所有这些状态均不变后才能跳过，收益需先测量。

## 四、结构查询

每玩家缓存维度、方块坐标、当前日记 JourneyId、剩余结构集合与上次检查时间。位置变化继续按原来每秒频率检查，不按区块粗略缓存；同一区块内可能跨越结构边界。

静止时无变化的负结果最多复用 5 秒；结构数据重载、换日记、跨维度、进度变化立即失效。正结果立即写入进度后从剩余集合移除。若目标数据更新不能可靠监听，5 秒 TTL 是兜底，而不是无限期缓存。

这会让静止时新生成结构的识别最多延迟约 5 秒，不影响移动探索的原检查频率。不主动加载区块。六类剩余结构合并用 LinkedHashSet，消除 contains 去重的平方级扫描。

## 五、物品提示与字体

DiaryDialogue 对苦旅/归乡分别缓存少量最近排版结果，键包含正文类型、有效宽度、语言、字体资源代次、玩家名。退出与资源重载清理；可变 Component 返回副本，防止其他模组污染缓存。阅读提示、进度条、物品状态不进入静态正文缓存。

光泽时间仍每帧更新，缓存排版不会冻结动画。缓存 16 个光晕方向偏移，避免逐帧 sin/cos 和不必要对象；暂不减少采样，不改变用户已接受的外观。

普通字体的标记检查应避免为每个调用创建 int[]、boolean[]；若采用渲染线程专用复用 sink，要保证重入安全，不能用一个无保护的共享对象。渲染管线包装不能按连续变化的 originX 永久缓存，避免内存增长。

## 六、验证和实施顺序

1. 默认关闭的诊断 + 随机池快照 + 提示缓存 + 清除列表 O(1) 移除：优先实施，不改普通玩法。
2. 效果来源标记与 Sounds 定向过滤：单独实现和验证，客户端/服务端同时升级。
3. 清除尝试预算、结构 TTL、循环提示限频：明确极端情况下的延迟/行为变化后实施。

验证场景包括：少量与数百种效果稳定驻留；同 ID 续时/升级；自动到期；静止自动净化与外部补回；未反转战斗清增益；拒绝移除的效果；手动喝药覆盖同 ID；掉线/跨维度；高延迟和同 tick 增删；无 Sounds 和不兼容版本。

分别测服务端 tick 时间、客户端 CPU/分配量、每秒效果包与声音调用数。不以“声音没了”认定服务器成本已消失，不以微基准代替整合包测试。
